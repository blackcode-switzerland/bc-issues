## THE FAILURE MODE THIS PHASE HAS — READ THIS TWICE

Phase 3 failed loudly. Phase 4 quietly. Phase 5 later. Phase 6 slowly.

**Phase 7 fails DESTRUCTIVELY. It is the first phase where a bug deletes user
data that cannot be recovered.**

lib/blob-gc.ts runs sweepOrphanedUrls on USER ACTION — hard-deleting a comment,
purging from Trash — not on a schedule. It calls Vercel Blob `del()`. There is
no undo, no Neon branch, no snapshot. A scanner that misses a reference makes a
still-referenced file vanish; a purge that runs against the wrong store deletes
production bytes.

Therefore, non-negotiable:

- **A scanner that returns nothing must be treated as an ERROR, not as "no
  references".** The current code's safety comes from scanning everything; a
  registry makes "no scanner registered" a silent path to deletion. Fail closed.
- **Prove the negative before trusting the positive.** Register a second,
  fake app scanner in a test that claims a reference, and assert the delete is
  REFUSED. A GC test that only proves deletion works proves the dangerous half.
- **Never point a non-production environment at the production Blob store.**
  Preview has its own store for exactly this reason. Verify
  BLOB_READ_WRITE_TOKEN scoping before any GC path runs anywhere.
- **Do not run a GC sweep against production as "verification".** Verify with
  reference COUNTS and refusals. The only production delete should be one you
  can point at a specific test file you uploaded yourself.


## HARD RULES

- Rehearse the migration AND the rollback on a fresh Neon branch.
- PREVIEW DEPLOY REQUIRED — migration plus blob paths. Preview env is configured
  (DATABASE_URL as issues_app on the preview branch, NEXTAUTH_SECRET, the
  separate preview Blob store).
- Decide the cutover ORDERING explicitly and follow the RUN_MIGRATIONS table.
  Deploy-first means postbuild owns the migration — remove RUN_MIGRATIONS first.
  Confirm additivity before relying on the no-outage-window property.
- Run `vercel deploy` FROM THE REPO ROOT. From apps/issues it uploads only that
  directory and npm install 404s on the workspace packages.
- Deployment Protection blocks `bk` from authenticating against a deployment
  URL. Plan to verify end-to-end at the post-promote step with the PUBLISHED
  binary, not on the staging URL. Do not add an automation bypass secret.
- `vercel deploy --prod` and `vercel promote` are BLOCKED for you by the
  permission classifier. Probe the blocked command BEFORE anything irreversible.
  Hand exact commands to the user.
- NEVER raise CLI_MIN_VERSION — Phase 8.
- If you release a CLI: web deploy -> release.sh cli minor (answer `normal`,
  never `forced`) -> web deploy again -> verify x-bk-cli-latest.
- Ask before: applying any migration to main, any Vercel env change, promoting
  to production, publishing to npm, deleting any Neon branch or Blob object.
