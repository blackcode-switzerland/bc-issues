## YOUR TASK — PHASE 8, IN THIS ORDER

The plan's Phase 8 section is authoritative for items 2-6. Item 1 is a blocker
inherited from Phase 7 and comes first.

### 1. THE BLOCKER — cross-deployment blob reference checking

Read "OWED BEFORE APP #2" in the plan. In short: Phase 7's scanner registry
correctly refuses to delete a blob unless every enabled app proves it holds no
reference — but per-app Postgres roles mean the issues deployment can never read
sales tables, so it can never obtain that proof. The moment a second row lands in
platform.apps, blob deletion stops working entirely.

Recommended shape (option A in the plan): platform.blob_references
(url, app, source_urn), written in the SAME TRANSACTION as the content change
that creates or removes a reference, plus a `bk super-admin blob-drift`
reconciler. This is exactly the platform.entities pattern from Phase 6 — same
risk, same proven mitigation.

You may argue for option B or C if you find A does not hold. Do not loosen the
delete gate; that is not on the table.

**Everything else in this phase is a lie until this ships.** A checklist that
says "adding an app is nine steps" while step ten is "storage cleanup silently
stops working" is worse than no checklist.

### 2. The four carry-forwards

  - `bk trash` refs are internal database ids (issue:905) — the one place the
    platform exposes a work-item serial instead of its #number. DECIDE: map them
    to #number, or document Trash as a deliberate exception in the guide. Do not
    leave it undecided a third time.
  - `bk undo` is INERT — logTransaction has no callers, so platform.transaction_log
    is never written. A documented agent-facing feature that does nothing is
    worse than a missing one. Fix it or remove it and say so in the changelog.
  - app/api/openapi.json/route.ts still exists as a 410 stub while CLAUDE.md says
    the spec was deleted. Reconcile code and doc.
  - Tighten events.app AND uploads.app to NOT NULL, once no deployed code can
    write a NULL. Verify that precondition rather than assuming it.

### 3. Missing guardrails

  - platform-storage, platform-auth and platform-agent have NO ESLint config, so
    `npm run lint` does not check three of six packages. Add configs.
  - CLI-parity test must run PER APP.
  - Guide test: a topic under topics/<app>/ may not name another app.
  - ESLint: no apps/<a> -> apps/<b> imports.
  - A test asserting no app queries another app's schema.
  Every guardrail you add, PROVE IT FIRES: break something deliberately, watch
  it fail, restore. A guardrail you have not seen fire is one you cannot claim
  works.

### 4. apps/_template/

A minimal working app: one entity, one route, one CLI command group, one guide
topic, one page. **It must build and pass the parity test on day one.** A
template that does not run is worse than no template.

### 5. docs/adding-an-app.md

The ordered checklist — packages deps and apps/<name>/ from the template;
CREATE SCHEMA + role + grants; a row in platform.apps; commands + routes
annotations; guide topics; docs/changelog/<app>.md; Vercel project pointed at
the EXISTING Neon project and Blob store; Root Directory; subdomain; app docs.

**Then actually follow it**, end to end, against apps/_template. Time it. Write
down what hurt. A checklist nobody has walked is a draft.

### 6. The extraction rehearsal

Actually run it: `pg_dump --schema=issues`, stand it up beside a vendored copy of
the platform packages, confirm it boots. This validates the "we could sell one of
these" claim from PLATFORM-ARCHITECTURE.md §11 while it is still cheap to fix.

### 7. Docs, then the floor

  - Rewrite CLAUDE.md and AGENTS.md for the finished monorepo.
  - Final CLI release in the documented three-step order.
  - **RAISE CLI_MIN_VERSION LAST, and as its own change.** Target 1.10.0 — the
    first namespaced version. Publish first, confirm adoption via
    x-bk-cli-latest having been advertised for long enough that installed
    clients have seen the nudge, and only then raise the floor. Raising it
    strands every user with nothing to upgrade to. This is the single most
    dangerous one-line change in the whole migration.
